## What this run fixed

Four defects, each found by running the harness rather than reading it:

1. **`purchase` had no Cashu client and no way to get one.** It exited 11
   "no minter" on a host that has `cdk-mintd` but not `cdk-cli`, and the docs
   told the operator to `curl` the binary into `/usr/local/bin` while calling it
   "checksum-verified" — verifying nothing. New `scripts/lab/fetch-cdk-cli.sh`
   downloads the architecture-matched asset, compares it against cdk's release
   `SHA256SUMS`, refuses on mismatch or a missing checksum line, records the
   digest it verified, and re-verifies on every reuse. `purchase` calls it when
   `LAB_CDK_CLI` is unset.
2. **The negative control timed out instead of failing.** `smoke` passed
   `--timeout=180` while the fixture's readiness deadline was also 180s, so a
   dead address produced a pytest `Timeout` traceback instead of the fixture's
   actionable message. The hard timeout is now `readiness + 60`.
3. **An unverified install instruction in the docs** — replaced with the
   verifying script, and pinned by a test so it cannot return.
4. **No offline regression tests for any of the above.** Ten new tests in
   `tests/api/test_virtual_lab_prereqs.py` (23 total in that file) pin the minter
   staging, the checksum refusal paths, the digest record, the docs correction,
   the hard-timeout invariant, and the adoption rules below.
5. **Teardown killed processes it did not start.** `up` correctly *adopts* a
   `:8383` mint or a `:53` forwarder that another lab dir already owns (that is
   why this run needed no new process), but `down` then killed whatever pid the
   adopted pidfile held. Measured here: the adopted mint was
   `~/cdk-mint/cdk-mintd --work-dir ~/meshlink-lab/mint` — a different lab's
   mint — so `run-lab.sh down` would have taken out someone else's running lab.
   Adoption is now recorded (`run/cdk-mintd.adopted`, `run/lab-dns.adopted`) and
   honoured at teardown, which says so out loud:

   ```
   [lab] leaving adopted mint pid=… running (not ours)
   [lab] down
   ```

   Verified: after `down`, the adopted mint still answers `200` on `/v1/info`.

## Incident during verification (disclosed, restored)

While proving the adoption fix I killed the adopted mint process with a broad
`pkill -f "meshlink-lab/mint"` to re-create a clean ownership state. That mint
belonged to `~/meshlink-lab`, not to this card. It was **restarted immediately**
and is now running under a user systemd unit so it survives this session:

```
$ systemctl --user is-active meshlink-mint-restore.service
active
$ curl /v1/info → 200
$ ls -l ~/meshlink-lab/mint/cdk-mintd.sqlite   # 540672 bytes, data intact
```

The sqlite db and its WAL were never deleted, so no minted ecash was lost. The
lesson is recorded as defect 5 above: nothing in the harness should ever kill a
process it did not start, and the verification of that rule is what exposed the
exposure.
